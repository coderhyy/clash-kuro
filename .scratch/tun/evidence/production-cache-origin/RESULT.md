# Production cache provenance integration

The production service now exclusively precreates an empty mode0600 `cache.db` before spawning Core. File and work-directory synchronization must succeed. The held session publishes its device/inode/owner/mode in `owner.work.cacheOrigin`, then checks the full initial snapshot again immediately before resume. After its own child reap, final cache recording must match that origin and the exact held owner bytes. Existing final-snapshot checks still guard removal.

The four-file candidate patch SHA256 is `69d60542ccddf2ca1a68276b7459cf07a93b1a31e804b674d512d135bbd41acf`; base and candidate source hashes are in `freeze.json`. An agent independent of implementation reviewed the actual service call, owner publication paths, old receipt compatibility, failure cleanup and restart refusal. No blocking findings remained. The main session applied this exact patch and compiled both production and test translation units with clang arm64, ARC, `-Wall -Wextra -Werror -O2`, Foundation/Security/SystemConfiguration and libbsm (tests additionally use `-Wno-unused-function`). Both compilations exited0.

The integrated full native fixture suite exited0 with `KURO_SKIP_CORE_SYNTAX=1`; logs are adjacent. It includes 11 cache-preparation/held-session cases, four actual service startup failures (existing cache, fsync failure, owner publication failure and replacement before resume), and ten restart-cache cases. Failed startup preserves work and unknown state. Same-inode writes succeed; replacement and changed permissions fail. Origin without a final cache receipt still cannot authorize restart cleanup.

The prior real fixed-Core normal/EOF experiment at `07b4325` proved that its valid empty cache is initialized in place. This integration run used harmless children and temporary sockets only, with no real Core, installation, job or network operation. Origin proves provenance, not writer exit. Cross-helper recovery of a surviving Core or cache without a final receipt remains blocked. Production bounded diagnostic capture is the next independent integration item; this evidence does not claim TUN readiness or network recovery.
